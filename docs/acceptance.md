# 验收文档：IDS 序列网页渲染（ids-font-tools）

> 日期：2026-11-20 · 状态：**已验收（方案 A · SVG 动态合成）**
>
> 项目目标：给定 IDS 序列（如 `⿰𠦝一`），从中华书局宋体（三平面 TTF）找到所需部件并拼成单字，在网页中展示。
> 立项时要求三种方案（A SVG 动态合成 / B OpenType 连字 / C 图片字库）全部实现并对比，验收后保留最优方案。

---

## 1. 验收结论

**保留方案 A（SVG 动态合成），删除方案 B/C**（代码见 git 历史，评估结论保留于本文档第 6 节）。

| 验收项 | 结果 |
|---|---|
| `⿰𠦝一` 渲染为完整单字 | ✅ 浏览器实测通过 |
| 任意嵌套序列（⿰⿱十早一等 8 例） | ✅ 全部通过 |
| 合成字符合字体标准大小 | ✅ 与真实字形 ink 对照：高差 ≤2.5%、垂直中心偏差 <1.5‰em |
| 缺字兜底（⿰明一 → ⿰日月 递归） | ✅ 浏览器实测通过 |
| 单元测试 | ✅ 15/15（解析合法性 / 布局守恒 / faceBox / 兜底） |
| TypeScript | ✅ `tsc --noEmit` 零错误 |

关键事实更正（项目早期拦截）：**`𠦝` 的码位是 U+2099D**。网络资料常误写 U+2599D——那实际是 `𥦝`（⿱穴林，CHISE 实证）。此码位错误如未拦截，后续所有字体查询将全部查错字。

## 2. 最终方案（A · SVG 动态合成）

### 2.1 管线

```
IDS 字符串  ⿰𠦝一
    │ core/parse.ts        （移植 parse-ids，MIT；前缀式 12 运算符 → AST）
    ▼
AST
    │ core/layout.ts       （SPLITS 子格切分 + 各向异性 fit → LayoutNode 树）
    │   ├── core/glyphStore.ts  （码位 → 字形 path；跨三字体 cmap 路由；faceBox）
    │   └── 缺字？→ CHISE 兜底 IDS 递归拆解（如 𠦝 → ⿱十早）
    ▼
LayoutNode 树
    │ components/IDSRenderer.tsx  （遍历生成 JSX <g transform><path/>）
    ▼
SVG 单字（悬停联动构件树）
```

### 2.2 关键设计决策

1. **布局引擎单一实现**：核心（parse/layout/glyphStore）为框架无关纯函数，React 只是薄壳——评估期间方案 B（离线字体注入）与 C（离线 SVG 导出）经 tsx 直接 import 同一 core 复用布局，避免双实现漂移。
2. **标准字面框（faceBox）**：根 cell 不用整个 em 方格，而用从原字体统计的字面框（69 个常用全尺寸汉字 ink 的包络 `[11,-140,1013,864]`，约 98% em），SVG 视口为完整行框（em + hhea descent = `1000×1234`）——合成字与真实汉字同大、同样伸入基线下方、可正确混排。
3. **各向异性部件适配**：真实 CJK 排版中左右结构部件全高横向压缩（非等比）；叶节点按 ink bbox 各轴独立适配子格，拉伸钳制在等比的 2× 以内，防止「一」「丨」类笔画部件被拉粗变形。
4. **兜底可追溯**：兜底拆解的节点在构件树与 SVG 中带 `inferred` 标记，多描述时取首个、其余留作候选（响应调研文档「多对多、输出候选+证据」的原则）。

### 2.3 目录（验收时）

```
tools/extract_glyphs.py     三字体 cmap 合并路由 + faceBox 统计 + 字形提取
tools/build_fallback.py     CHISE/cjkvi-ids 高频构件 → 兜底映射（2686 字，71 KB）
testcases/ids.txt           8 例（目标例/嵌套/三元/包围/基准）
web/src/core/               parse · glyphStore · layout（+ 15 例单测）
web/src/components/         IDSRenderer · IdsText（运算符内联 SVG）
web/src/App.tsx             单页应用（输入/字号/用例 chips/构件树联动/复制）
```

## 4. 遇到的问题与解决（按层分类）

### 4.1 事实与数据层

| 问题 | 现象与发现 | 解决 |
|---|---|---|
| **`𠦝` 码位以讹传讹** | 初查 U+2599D 有字形，但 CHISE 显示 U+2599D = `𥦝`（⿱穴林）；`𠦝` 实为 **U+2099D** | 用 `ord('𠦝')` + CHISE 双重核实后重测；此错误列为项目第一警示 |
| **三字体覆盖互斥** | 00 平面（BMP+运算符）无 U+2099D；02 平面（Ext B-F）无 U+4E00——任一字体都无法独立拼出 `⿰𠦝一` | extract_glyphs.py 内建 cmap 合并路由：按 00→02→15 顺序查表，命中即取 |
| **官方数据源无 IDS** | Unihan（18.0.0，148 万条）实测不含任何 IDS/构件分解字段 | 拆解数据改用社区库 CHISE-IDS + cjkvi-ids（与调研文档结论一致） |
| **目标序列不在数据库** | `⿰𠦝一` 在 CHISE/cjkvi 全库 grep 无匹配 | 确认这正是本项目价值：渲染**任意**自定义序列，而非查库回放 |
| **兜底映射体积** | 全量 CHISE 映射 93,420 条、数 MB，不适合随网页分发 | 只保留出现频率前 3000 的构件字映射（2686 条、71 KB），运行时缺字才查 |

### 4.2 解析层

| 问题 | 现象 | 解决 |
|---|---|---|
| 自造用例写错运算符 | `⿱一一大`（想表达三层）解析失败——`⿱` 是二元，吃掉 `一一大` 前两个后剩 `大`，`parse` 严格返回 null | 更正为三元 `⿳一一大`；此事件反向验证了 parser 的严格性（多余字符必须报错而非静默吞掉） |
| 运算符版本覆盖 | parse-ids（MIT）只覆盖 12 种经典运算符；中华书局 2021 版字体也不含 Unicode 15.1 新增的 ⿼⿽（实测缺 U+2FFC/2FFD） | 确认 12 种覆盖本项目全部用例；新运算符列为后续扩展 |
| CHISE 私有引用 | IDS 数据含 `&GT-xxx;` 等 HTML 实体引用（无对应 Unicode 字符） | 保留 parse-ids 的 html 节点类型，渲染为缺字占位并在树中可见 |

### 4.3 布局层（本项目最深的迭代）

| 问题 | 现象与发现 | 解决 |
|---|---|---|
| **无现成布局规则可抄** | KAGE Engine 的部件比例内嵌在 GlyphWiki 数据的显式坐标中（非算法）；kage-engine/ipfs-ids-find 源码确认均无可复用的「运算符→比例」规则 | 自建 SPLITS 表（12 运算符 → 子格矩阵），并列出可调参数 |
| **IDS 运算符「tofu」误报** | 视觉评审报告 ⿰ 显示为「虚线框缺字」；DOM 证实 SVG 已渲染 | 读取字形 path 发现全由短线段构成——**字体的 IDS 运算符字形本就是 Unicode 标准的虚线格示意图**，属误报。同时真正解决 UI tofu：运算符字形从字体提取，经 IdsText 内联渲染 |
| **等比缩放导致合成字矮小**（关键缺陷） | ink 对照实证：`⿰𠦝一` 合成 ink 高仅 522/1024em，真实 `朝`（⿰𠦝月）为 978——真实排版中左右结构部件**全高、横向压缩**（非等比变换），等比 min 缩放让部件按宽缩小、垂直留白 | fitLeaf 改**各向异性缩放**（各轴独立适配子格）+ **2× 拉伸钳制**（防笔画部件变形）；修正后高差 2.5% |
| **字面率与基线位置** | 旧实现 ink 撑满 em 方格（≈100%），且视口只覆盖基线上方——真实字 ink 约 98% em 且伸入基线下 ~14%（descender） | ① 统计 69 常用字 ink 包络得 faceBox 作根 cell；② 视口改为完整行框 1000×1234（em+hhea descent）；修正后垂直中心 362 vs 真实 361（几乎精确） |
| 部件间设计留白未建模 | 合成字比真实字宽 6.9%~14.5%（真实「明」的日月间有大间隙） | 已知限制：SPLITS 表预留 gap 参数位，列为后续调参项（不影响标准大小验收） |

### 4.4 字体工程层（方案 B 期间，结论仍有参考价值）

| 问题 | 现象 | 解决 |
|---|---|---|
| GSUB 表组装崩溃 | `font['GSUB'] = ot.GSUB()` 保存时 `compile() missing 'font'` | otTables.GSUB 是内层数据结构，需经 `newTable('GSUB')` wrapper 包装（`.table` 属性持有数据）后挂载 |
| 字段名大小写 | 4.60 中 `lookupFlag` 赋值无效——编译读规范名 `LookupFlag`/`LookupType`/`LigGlyph` | 逐类打印 `getConverters()` 的规范字段名后统一改用大写 |
| SVG path 解析坑 | SVGPathPen 输出含 `V`/`H` 紧缩命令与 M/Q 的隐式参数重复 | 重写带状态的流式解析器（V/H 依当前点展开为 L；隐式重复按 SVG 规则处理） |

### 4.5 浏览器与工具链层

| 问题 | 现象 | 解决 |
|---|---|---|
| **IDS 序列连字被整形分段阻断**（方案 B 核心发现） | `⿰𠦝一` 连字不生效（宽度恒 300px=3 字符） | **对照实验定位根因**：加纯汉字规则 `日+月→明形`，汉字序列连字成功（200px→100px）——GSUB 本身有效；阻断出在浏览器 itemizer 把 Common script 的运算符与 Han 分字分入不同 shaping run，跨 run 规则永不匹配。结论：方案 B 在浏览器对 IDS 序列**原理性不可行**（与字体质量无关） |
| FontFace 缓存假象 | 重建字体后「日月」连字消失（200px） | URL 加 `?t=Date.now()` 破缓存后恢复 100px——排查字体 bug 前先排除缓存 |
| IAB 自动化点击超时 | Playwright `click()` 在 actionability 检查超时（元素存在、`force` 无效） | 改用 `evaluate()` 页内原生 `.click()`（React 合成事件可冒泡） |
| 截图管线偶发超时 | screenshot "surface preparation timed out" | 改用 DOM 快照 + `evaluate` 宽度测量等客观手段（连字判定即此法） |
| vite 仅 IPv6 | dev server 绑 `::1`，`127.0.0.1` 连接被拒 | 统一用 `localhost` 访问；5173 被占时看启动日志换端口 |

## 6. 三方案评估结论（为何保留 A）

| 方案 | 评估结论 | 取舍 |
|---|---|---|
| **A · SVG 动态合成** | 任意序列即时渲染；构件可交互（悬停/字典入口）；字形库仅 16 KB；运行时个人使用、许可风险低 | **保留** |
| B · OpenType 连字 | 管线全部打通（合成字形/GSUB/逐字符显示正常），但浏览器整形分段使 **IDS 序列连字原理性不可行**（纯汉字序列可连字，但 IDS 必含 Common script 运算符）；即使可行也仅适合固定字集、且衍生字体再分发有方正授权风险 | 删除（代码见 git 历史；若未来在本地排版引擎/打印管线中使用，字体工艺路线已在本文 4.4 节留档） |
| C · 图片字库 | 功能正常（8 SVG + manifest），但本质是 A 的预渲染缓存：任意新序列需重跑导出、无交互、字形文件再分发同样有授权风险 | 删除 |

## 7. 使用与再生成

```bash
python3 tools/extract_glyphs.py      # glyphs.json（faceBox + 字形，含 IDS 运算符）
python3 tools/build_fallback.py      # chise-fallback.json（2686 高频构件兜底）
python3 tools/prepare_web_fonts.py   # fonts/zhsw-*.ttf + zhswRanges.ts（@font-face 按需渲染原字体）
cd web && npm install && npm run dev
```

组件用法：`<IDSRenderer ids="⿰𠦝一" db={db} size={180} onHover={...} />`

## 8. 已知限制与后续方向

1. **部件间留白（gap）未建模**：合成字比真实字宽 6.9%~14.5%，主因是真实字部件间的设计留白（如「明」）；SPLITS 表可加 per-operator gap 参数
2. **Unicode 15.1+ 新运算符**（⿼⿽ 等）：字体与 parser 均未覆盖（原字体 2021 版无这些码位）
3. **`⿻` 叠加结构**：目前两构件同格叠放，未做笔画级避让
4. **兜底策略**：多描述取首个；可结合笔画数（Unihan kTotalStrokes）做候选排序
5. 字形库覆盖：当前仅 testcases 所需 25 字 + 运算符；扩字集只需给 extract_glyphs.py 传参，无需改代码

## 9. 增量交付：合字工坊（判定链 + 真字形预览）

> 验收后新增需求：合字输入框与预览图，含 Unicode/字体两级收录判定，字体已收录则直接用字体渲染，否则用方案 A 合成。

### 9.1 判定链设计

```
输入 IDS
  ├─ parse 失败 → 解析错误提示
  ├─ 反查 ids-unicode-index（98,305 键，CHISE+cjkvi 全量）
  │    ├─ 命中（可多候选，同描述异码位，可点击切换）
  │    │    ├─ 字体三平面 cmap 有该码位（fontFlag）→「字体已收录」
  │    │    │    ├─ 字形数据已提取（高频 3000 字）→ 预览【字体真实字形】GlyphView
  │    │    │    └─ 字形数据未提取 → 预览【方案 A 合成】+ 如实标注降级原因
  │    │    └─ 字体无该码位 →「字体未收录」→ 预览【方案 A 合成】
  │    └─ 未命中 →「Unicode 未收录」（口径注明：未命中 ≠ Unicode 绝对未收录）→ 方案 A 合成
```

要点：

- **Unicode 收录判定口径 = 社区库反查**（Unihan 无 IDS 字段，这是调研阶段已实证的约束），界面明示此口径
- **判定与渲染分离**：「字体已收录」按三平面 cmap 全量判定（134,286 码位，全部内置于索引 fontFlag）；「真字形渲染」取决于 glyphs.json 是否已提取该字形（高频构件 3000 字）。两者不一致时如实标注（如 `⿱十早` 的候选 U+9FBA：已收录但字形未提取 → 合成显示并说明）
- **多对多**：同一 IDS 可对应多个码位（`⿱十早` → U+9FBA / U+2099D），全部列出为候选 chip，可切换预览——贯彻调研文档「候选 + 证据」原则
- 真字形视图（GlyphView）与合成视图共用行框几何（em+descent），两者可公平对比大小

### 9.4 体积权衡

### 9.5 缺陷修复案例：`⿰亻革` 误判「未收录」（数据源时效性）

**现象**：用户输入 `⿰亻革`，判定显示 Unicode 未收录；实际该字已收录为 **U+313BC 𱎼**（CJK 扩展 H，Unicode 15.0 / 2022-09，IRG 来源 UTC-02973，读音 gě）。

**排查过程（逐层实证）**：

1. 本地 Unihan 18.0 grep `U+313BC` → 存在（kMandarin gě）——用户报告属实
2. 旧数据源 grep → `references/chise-ids`（GitHub osfans 镜像，快照 **2021-08-20**）与 `references/cjkvi-ids`（快照 **2019-02-07**）均无 U+313BC、也无 `⿰亻革` 描述
3. 两镜像上游本身已停更（fetch 无新提交；cjkvi 远端也无 ext-g/h 文件，其扩展区文件止于 `ids-ext-cdef.txt`）

**根因**：**数据源快照时间窗错位**——Ext-H 于 2022-09 才进 Unicode，2021/2019 年的快照天然不含它。检测逻辑本身无 bug（索引如实反映了源数据）；界面上的口径注记「未命中 ≠ Unicode 绝对未收录」正是为此类情形设计，本案例是该注记的活例证。

**修复**：

1. 数据源替换为 CHISE 活跃上游 `github.com/chise/ids`（快照 2026-11-17，含 `IDS-UCS-Ext-{A,B,C,D,E,F,G,H,I,J}` 全套扩展区文件）；实测 `IDS-UCS-Ext-H.txt:110` 正是 `U+313BC 𱎼 ⿰亻革`
2. 重建索引：98,305 → **107,445 键**（+9,140，新进 Ext-G/H/I/J 描述）；兜底映射同步重建
3. 顺带修复一个提示文案缺陷：预览降级提示原先不区分「字体未收录」与「字体已收录但字形未提取」两种情形（`⿰亻革` 实测暴露），已按候选 inFont 分流

**修复后实测**（浏览器）：`⿰亻革` → **Unicode 已收录 𱎼 U+313BC**（候选 chip 标注 字体✗）→ 中华书局宋体 未收录（fontTools 复核：15 平面字体在 Ext-H 区间 31350–323AF 共 **0 字**，判定如实）→ 预览方案 A 合成（亻/革 字形齐备）。

**遗留限制（如实声明）**：社区库快照永远存在滞后窗口（新收录字进入 CHISE 需时间）；「未收录」结论应理解为「当前数据源快照内无记录」。界面口径注记即为此保留。数据源建议定期 `git -C references/chise-ids pull` 后重建索引。

### 9.6 预览交互改版：收录即并排对比（真字形 × 方案 A 合成）

**需求**：字体已收录时始终显示字体中的字形，同时并排显示方案 A · SVG 合成以便对比——替代原先的「二选一分流」（收录且有字形 → 只显真字形、构件树停用；否则只显合成）。

**改动**（`web/src/App.tsx` Preview 组件 + `index.css`）：

1. 分流条件从「有真字形数据」放宽为「候选 inFont」：收录即进入**对比模式**，左侧 `GlyphView` 真字形、右侧 `IDSRenderer` 合成，各自带来源标签与说明
2. 构件树不再停用（合成视图始终在场，树恢复为合成的拆解说明，悬停联动保留）
3. 字形数据未提取的收录字（高频 3000 之外，如 `⿱十早` 首选 U+9FBA 龺）：`GlyphView` 内建回退为系统字体文本代显，hint 如实标注「字形数据未提取，系统字体代显」，不冒充宋体字形；需真字形可 `extract_glyphs.py` 追加码位重建
4. 顶部徽章随模式切换：「对比模式：字体真实字形 × 方案 A 合成」/「方案 A · SVG 合成」

### 9.7 缺陷修复案例：「系统字体代显」渲染成横条乱码（U+27BAD 𧮭）

**现象**：输入 `⿰谷丸`（= U+27BAD 𧮭，Ext-B，字体已收录但字形未提取），左侧「字体真实字形」框渲染成**六条水平黑条**，判定候选 chip 里的小字同样乱码；hint 却声称「系统字体代显」。

**根因**：回退设计错误——`GlyphView` 对未提取字形裸渲染 `<span>{ch}</span>`，把希望寄托在系统字体上；而 macOS 系统字体对 Ext-B 以上的生僻字**同样没有覆盖**，WebKit 用 LastResort 类字形（横条）显示。「代显」是个无法兑现的假承诺。

**方案选型**（先量化再动手）：

| 候选 | 评估 | 结论 |
|---|---|---|
| 全量提取收录候选字形 | 索引实测：收录候选 **88,066** 字、缺 **85,389**，按 1KB/字形 ≈ **87 MB** | ❌ glyphs.json 现 3MB 已是急切加载 |
| 按需提取（服务端） | 项目是纯静态 demo，无服务端 | ❌ |
| **@font-face 直接渲染原 TTF** | 本地就有三平面 TTF（17/40/24 MB），`unicode-range` 命中才下载对应平面；浏览器光栅化 = 真宋体字形，零提取 | ✅ |

**实现**（`tools/prepare_web_fonts.py` + `web/src/core/zhswFont.ts` + `GlyphView.tsx`）：

1. `prepare_web_fonts.py`：TTF 净化重存到 `web/public/fonts/zhsw-{00,02,15}.ttf`，并从 cmap 生成 `zhswRanges.ts`（unicode-range 描述符，仅 CJK 区段 ≥ U+2000）
2. `zhswFont.ts`：三个 FontFace 同族 `ZHSW-Web`，按 **15→02→00 顺序注册**（同族后注册者优先）——三平面 cmap 在 BMP 有零星重叠，此序使重叠段由 00 胜出，与 `extract_glyphs.py` 的 00→02→15 提取路由一致；`preloadZhsw(ch)` 经 `document.fonts.load` 触发按需下载
3. `GlyphView` 未提取分支：裸 span → `ZhswChar`（ZHSW 栈 + 行框比例与 SVG 视口对齐 + preload）；候选 chip 同步接入（用户截图里 chip 乱码同源）
4. hint 文案改为如实口径：「按需加载宋体 TTF 由浏览器渲染真字形」

**过程中撞上的第二层问题**：00 平面 FontFace 一律报 `NetworkError`/「Invalid font data」而 02/15 正常（fetch 完整 200 返回 18MB，解码层拒收）。**变体二分定位**：构造「只剔 cmap(1,0) 子表」与「只剔 hinting 表」两变体分别试探 → 前者 LOADED、后者仍拒收 → **元凶是 00 平面畸形的 (1,0) format 0 Macintosh cmap 子表**（02/15 的同名子表无恙，fontTools 也能解析，仅 WebKit OT sanitizer 拒收）。处方并入脚本：cmap 只保留 platform 3 子表（(3,1)/(3,10)，CJK 映射完整）+ 剔 vhea/vmtx/GSUB。

**验证**（浏览器 + 独立证据链）：

| 输入 | 场景 | 结果 |
|---|---|---|
| `⿰谷丸` U+27BAD（02 平面） | 原缺陷场景 | 左框真宋体字形（谷+丸），chip 正常；FontFace 02=loaded |
| `⿱十早` U+9FBA 龺（00 平面） | BMP 未提取 | 左框真字形 + chip 正常；FontFace 00=loaded（拒收已修复） |
| `⿰日月` / `⿰𠦝一` | 回归 | SVG 真字形 / 单框合成，行为不变 |

字形正确性三方对证：① fontTools 直接 dump TTF 轮廓（U+27BAD 实为谷+丸，与 CHISE `IDS-UCS-Ext-B-4.txt:7087` 一致）；② 300px 截图左右对比基本吻合；③ **像素指纹**：canvas 以 ZHSW-Web 与 PingFang 各渲染「龺」相差 1552px（自绘噪声 0）→ 页面确实在用宋体原字体而非系统字体（advance 全宽 1em，宽度法无法区分，故用像素法）。

回归：`tsc` 零错误、单测 15/15。
